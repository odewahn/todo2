# Vibe-to-Cloud: Notes on Scaffolding and Deploying Apps with Claude Code Skills

## What This Is

This is a test of an idea: can we build a pair of Claude Code skills that let an ORM engineer
"vibe-code" a full-stack app locally and then deploy it to Cloud Run with minimal cloud knowledge
required? The two skills are:

- `scaffold-playground-app` — generates a complete Express + PostgreSQL + React/Vite starter
  project, pre-wired for local development via Dev Container and Docker Compose
- `deploy-cloudrun` — takes that generated project and deploys it to Cloud Run + Cloud SQL,
  handling the build, database provisioning, migrations, and DNS

The `todo2` app in this repo is the test vehicle: a minimal todo app with a Node.js/Express
backend, a React/Vite frontend, and a PostgreSQL database. It was generated by the scaffold skill,
developed locally inside a Dev Container, and then put through the deploy skill. Local development
worked fine. Deployment is what this document is about.

---

## The Intended Architecture

### App structure

The scaffold skill generates a multi-service layout:

```
todo2/
├── backend/    # Node.js/Express API, PostgreSQL via pg
└── frontend/   # React/Vite SPA, served via nginx
```

In production, these become two separate Cloud Run services. The frontend fetches from the backend
using `VITE_API_URL`, which is baked into the Vite build at deploy time.

### Database model

The deploy skill creates one shared Cloud SQL instance (`playground-postgres`) for the whole
playground. Each user gets one PostgreSQL database named after their GCP identity (e.g., `odewahn`).
Each app they deploy gets its own schema within that database (e.g., `odewahn-todo2`). The
`search_path` is set on the IAM role so application code queries tables without any schema prefix.

In theory this means:
- Many users share one Cloud SQL instance → lower cost
- Each user's apps share one database but are isolated by schema → easy teardown per app
- Migrations run against the schema, not the whole database

This model was not the result of deep deliberation — it emerged from the skill design. The schema
naming is also inconsistent between the two skills: the scaffold skill converts hyphens to
underscores (so `odewahn-todo2` becomes `odewahn_todo2`), while the deploy skill used the app
name directly, creating a schema with hyphens in the name. PostgreSQL allows this via quoted
identifiers, but it's a rough edge that should be reconciled.

## What Broke During Deployment

The blockers fall into two categories: bugs in the skill scripts themselves, and infrastructure
permission issues that require platform team involvement.

### Category 1: Bugs in the deploy skill

These are fixable by updating the skill.

**1. Wrong Cloud SQL tier**
The skill specifies `--tier=db-n1-standard-2`, which is a dedicated-core tier blocked by an org
policy in this GCP project. The fix is `--tier=db-f1-micro` (shared-core). The skill should
either use the correct tier from the start or handle this error gracefully.

**2. `PORT` is a reserved Cloud Run environment variable**
The skill tried to pass `PORT=3001` in `--set-env-vars`. Cloud Run rejects this — it injects
`PORT` automatically (defaulting to 8080). The fix is to remove `PORT` from the deploy command.
The app already reads `process.env.PORT || 3001`, so Cloud Run's injected value takes over
automatically.

**3. nginx hardcoded to port 80, Cloud Run expects 8080**
The scaffold skill generates an nginx config that listens on port 80. Cloud Run health-checks
the port defined by its injected `PORT=8080` env variable, so the container appeared unresponsive
and the deploy failed. The fix requires nginx to read `${PORT}` at startup via `envsubst`. This
was not accounted for in the scaffold skill at all.

**4. `--set-build-env-vars` is a beta-only flag**
The deploy skill uses `--set-build-env-vars` to pass `VITE_API_URL` into the Docker build. This
flag is not available in the GA `gcloud run deploy` — only in `gcloud beta run deploy`. The skill
needs to use the beta track for the frontend deploy command.

**5. `gcloud sql connect` fails on IPv6 hosts**
The skill uses `gcloud sql connect` to run schema setup SQL. On machines with an active IPv6
interface, this command fails with a Cloud SQL error about IPv6 not being supported. The fix is
to use the Cloud SQL Proxy v1 binary directly (`cloud_sql_proxy`) and connect via `psql`, which
also requires the `postgres` admin password to be set explicitly on new instances (it is blank
by default). The skill has no handling for any of this.

### Category 2: Infrastructure permission blockers

These require action from a platform/cloud admin and reveal assumptions baked into the skill that
don't match the actual permission model of the playground GCP project.

**The core assumption that failed:** The skill assumes the deploying user has
`resourcemanager.projects.setIamPolicy` — i.e., the ability to grant IAM roles at the project
level. The actual account used (`odewahn@oreilly.com`) only has
`roles/discoveryengine.notebookLmUser`.

This caused two downstream failures:

**A. The Cloud Run service account cannot connect to Cloud SQL**
The deploy skill creates a dedicated service account per app and grants it `roles/cloudsql.client`
and `roles/cloudsql.instanceUser` at the project level. Without these, the Cloud Run service
cannot open a connection to Cloud SQL via the Cloud SQL Auth Proxy at runtime. The services are
deployed, but any API call that touches the database will fail. The commands a project admin
needs to run are:
```bash
gcloud projects add-iam-policy-binding strong-keyword-184513 \
  --member="serviceAccount:odewahn-todo2-sa@strong-keyword-184513.iam.gserviceaccount.com" \
  --role="roles/cloudsql.instanceUser"

gcloud projects add-iam-policy-binding strong-keyword-184513 \
  --member="serviceAccount:odewahn-todo2-sa@strong-keyword-184513.iam.gserviceaccount.com" \
  --role="roles/cloudsql.client"
```

**B. The Cloud Run services are not publicly accessible**
The `--allow-unauthenticated` flag in the deploy command was silently ignored because granting
`allUsers` the `roles/run.invoker` role also requires `setIamPolicy`. Both services return
`403 Forbidden` to unauthenticated requests. A project admin needs to run:
```bash
gcloud beta run services add-iam-policy-binding \
  --region=us-central1 --member=allUsers --role=roles/run.invoker odewahn-todo2-backend

gcloud beta run services add-iam-policy-binding \
  --region=us-central1 --member=allUsers --role=roles/run.invoker odewahn-todo2-frontend
```

**C. Custom domain mapping is not possible without domain verification**
The skill expects to map `<app-name>.playground.gcp.oreilly.com` using Cloud Run's domain mapping
feature. This requires the domain to be verified in Google Search Console under the deploying
user's account. No such verification exists, so this step failed entirely. For the custom domain
pattern to work, either the verification needs to be pre-configured by an admin, or a different
DNS/routing mechanism needs to be used.

## The Bigger Permission Problem

The IAM issues above aren't just bugs to fix — they reveal a structural mismatch between what the
skill needs and what a typical playground user is likely to have. The skill was designed assuming
the deploying user is an admin. In practice they won't be.

There are a few ways to address this:

1. **Pre-provision shared IAM infrastructure**: An admin creates the Cloud SQL instance, a
   wildcard service account policy, and domain mappings once. Individual users then deploy into
   this pre-prepared environment without needing `setIamPolicy`.

2. **Use a shared service account**: Instead of creating a per-app service account, every app
   in the playground shares one service account that already has `cloudsql.client`. Isolation is
   then enforced at the schema level, not the IAM level.

3. **Terraform or a deployment API**: Platform team manages IAM via Terraform. The skill submits
   a request (e.g., via `gcloud run jobs`) rather than directly issuing `add-iam-policy-binding`.

The right answer depends on how much the platform team wants to pre-build vs. delegate.

## A Note on nginx and the Two-Service Architecture

The current scaffold generates a separate frontend Cloud Run service that uses nginx to serve the
built Vite static files. This was not a deliberate architectural decision — it just emerged from
the skill design — and it introduced most of the complexity in the frontend deployment (the port
mismatch, the need for `envsubst`, the `--set-build-env-vars` beta flag, and the CORS/`VITE_API_URL`
indirection).

For a vibe-coding/prototype context, this is probably the wrong default. A simpler approach worth
considering:

**Single-service: Express serves the Vite build**

The backend Express app can serve the compiled frontend as static files:
```javascript
app.use(express.static(path.join(__dirname, '../../frontend/dist')));
```

The Vite build runs once during Docker image construction (the Dockerfile builds both frontend and
backend). The result is one Cloud Run service, one URL, no CORS, no `VITE_API_URL` env var, and
no nginx. The Vite dev proxy continues to work locally unchanged.

The tradeoff is that you can't scale frontend and backend independently, and the image is slightly
larger. For the playground use case — small internal prototypes, not production traffic — that
tradeoff is almost certainly worth it.

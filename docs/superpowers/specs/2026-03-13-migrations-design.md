# Database Migrations Design

**Date:** 2026-03-13
**Project:** todo2
**Topic:** Wire up node-pg-migrate for manual database migrations

## Overview

Add `node-pg-migrate` to the backend to manage database schema changes as versioned migration files. Migrations are run manually by the developer. The first migration converts the existing `schema.sql` into a versioned migration file.

## Goals

- Replace `backend/schema.sql` with a proper migration-based workflow
- Work identically in the Dev Container (local) and against Cloud SQL (production)
- Keep it simple: no automatic migration on startup or deploy

## Non-Goals

- Automatic migration on app startup
- Automatic migration on Cloud Run deploy
- CI/CD integration

## Dependencies

- `node-pg-migrate` added as a devDependency in `backend/package.json`

## ESM Compatibility

`backend/package.json` uses `"type": "module"`, which makes all `.js` files ES modules. `node-pg-migrate` loads migration files via `require()` in its default mode, which is incompatible with ESM `.js` files.

**Resolution:** Migration files use the `.cjs` extension (e.g., `1_create_items.cjs`). Node.js always treats `.cjs` as CommonJS regardless of the package `type` setting. All generated migration files from `migrate:create` will also use `.cjs` via the `--migration-file-language cjs` flag in the script.

## npm Scripts

Three scripts added to `backend/package.json`:

| Script | Resolved command | Purpose |
|---|---|---|
| `migrate:up` | `node-pg-migrate up --schema $DB_SCHEMA --migrations-dir migrations` | Apply all pending migrations |
| `migrate:down` | `node-pg-migrate down --schema $DB_SCHEMA --migrations-dir migrations` | Roll back the last migration |
| `migrate:create` | `node-pg-migrate create --schema $DB_SCHEMA --migrations-dir migrations --migration-file-language cjs` | Create a new timestamped `.cjs` migration file |

`--schema $DB_SCHEMA` ensures all migrations run in the correct Postgres schema in both local and cloud environments. `DB_SCHEMA` is already set in `backend/.env` (locally) and injected by `deploy-cloudrun` in production.

`DATABASE_URL` is read automatically by `node-pg-migrate` from the environment — the same value already set in `backend/.env`.

### Creating a new migration

The migration name is passed as a positional argument after `--`:

```bash
npm run migrate:create -- add-priority-column
```

This produces a file like `backend/migrations/20260313120000_add-priority-column.cjs`. If the name argument is omitted, `node-pg-migrate` will error.

## Migration Files

- Location: `backend/migrations/`
- Extension: `.cjs` (CommonJS, required for ESM package compatibility)
- Naming: timestamp prefix generated by `node-pg-migrate` (e.g., `20260313000000_create_items.cjs`)
- First migration: `20260313000000_create_items.cjs` — creates the `items` table

### First migration

```js
exports.up = (pgm) => {
  pgm.createTable('items', {
    id: { type: 'serial', primaryKey: true },
    name: { type: 'text', notNull: true },
    created_at: { type: 'timestamptz', notNull: true, default: pgm.func('now()') },
  });
};

exports.down = (pgm) => {
  pgm.dropTable('items');
};
```

Note: `ifNotExists` is intentionally omitted. Migration idempotency is handled by the `pgmigrations` tracking table — each migration runs exactly once. Using `IF NOT EXISTS` would mask bugs where a table was created outside the migration system.

`node-pg-migrate` automatically creates a `pgmigrations` table in the target schema to track applied migrations.

## File Changes

| File | Action |
|---|---|
| `backend/package.json` | Add `node-pg-migrate` devDependency + three scripts |
| `backend/migrations/20260313000000_create_items.cjs` | New — initial migration |
| `backend/schema.sql` | Delete — superseded by migrations |

## Developer Workflow

### First time (new Dev Container or clean environment)

```bash
cd backend
npm run migrate:up
```

### Existing environment (schema already applied manually)

If you previously applied `schema.sql` by hand (e.g., an existing Dev Container volume already has the `items` table), running `migrate:up` will fail with a duplicate table error. Resolve by either:

1. **Recommended:** Destroy and recreate the Docker volume to get a clean database, then run `migrate:up`.
2. **Alternative:** Manually insert the first migration's record so `node-pg-migrate` skips it:
   ```sql
   INSERT INTO pgmigrations (name, run_on) VALUES ('20260313000000_create_items', NOW());
   ```

### Adding a new migration

```bash
cd backend
npm run migrate:create -- my-migration-name
# edit the generated file in backend/migrations/
npm run migrate:up
```

### Rolling back

```bash
cd backend
npm run migrate:down
```

### Against Cloud SQL (production)

Connect via the [Cloud SQL Auth Proxy](https://cloud.google.com/sql/docs/postgres/sql-proxy) running locally. The proxy exposes a local TCP socket (e.g., `localhost:5432`). Set `DATABASE_URL` to point at that socket, then run migrations:

```bash
export DATABASE_URL=postgres://<user>:<password>@localhost:5432/<db-name>
export DB_SCHEMA=todo2
cd backend
npm run migrate:up
```

`DB_HOST`/`DB_NAME`/`DB_USER` (the Cloud Run IAM path in `db.js`) are not used by `node-pg-migrate` — it reads only `DATABASE_URL`.

## Environment Variables

No new environment variables required. The existing `DATABASE_URL` and `DB_SCHEMA` values in `backend/.env` are sufficient for local development.
